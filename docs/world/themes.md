# Purpose

A theme defines the visual representation of semantic room data.

Themes let the same room layout be reused with different art. They map semantic cells — background, platforms and walls — onto tiles in a Godot `TileSet` without changing room topology or gameplay meaning.

---

# Separation of Responsibilities

The theme system is deliberately separate from the room bake pipeline.

```text
Room Bake Pipeline   →  RoomData + runtime room structure
Theme Build Pipeline →  ThemeInfo + TileSet + theme assets
ThemeApplyer         →  combines both on a runtime room
```

The theme build pipeline:

- is **not** part of `BakePipeline`;
- does not read or mutate `RoomData`;
- does not change collision, topology or semantic meaning.

The room bake pipeline only applies a theme at the end of baking through `ApplyDefaultThemeStep`. It does not build themes.

# Core Concepts

## Theme

A named set of visual assets for background, platforms and walls.

The current theme is `default`.

## Theme Assets

Editor-side source data:

- an Aseprite JSON metadata file;
- one PNG per named slice.

Theme assets live under:

```text
res://assets/sprites/themes/{theme}/{theme}.json
res://assets/sprites/themes/{theme}/{slice_name}.png
```

## Built Theme Resources

Generated by the theme build pipeline and stored under:

```text
res://resources/themes/{theme}/{theme}_tile_assets.tres
res://resources/themes/{theme}/{theme}_theme.tres
res://resources/themes/{theme}/{theme}_tileset.tres
```

Built theme resources are generated artifacts. Change the source assets or the build steps, then rebuild — do not treat the generated `.tres` files as a competing source of truth.

# Data Types

## ThemeTileAssets

Source-side catalog of variant names, before they are resolved to tiles.

```gdscript
class_name ThemeTileAssets
extends Resource

@export var platforms: TileAssetsPack
@export var walls: TileAssetsPack
@export var background: Array[String]
```

## TileAssetsPack

Variant names grouped by tile type. It is a `Resource` so it can be saved as part of `ThemeTileAssets`.

```gdscript
class_name TileAssetsPack
extends Resource

@export var single: Array[String]
@export var single_all: Array[String]
@export var single_top: Array[String]
@export var single_bottom: Array[String]
@export var single_left: Array[String]
@export var single_right: Array[String]
@export var top: Array[String]
@export var bottom: Array[String]
@export var left: Array[String]
@export var right: Array[String]
@export var full: Array[String]
@export var top_left: Array[String]
@export var top_right: Array[String]
@export var bottom_left: Array[String]
@export var bottom_right: Array[String]
```

## TilePack

Variant tiles resolved to `TileId` references. `ThemeInfo` uses this form.

It has the same fields as `TileAssetsPack`, but each field is an `Array[TileId]`.

## TileId

A serializable reference to one tile in a `TileSet`.

```gdscript
class_name TileId
extends Resource

@export var source_id: int
@export var atlas_coords: Vector2i
```

`TileId.at_source(source_id, atlas_coords)` is the convenience constructor.

## ThemeInfo

The runtime-facing theme definition.

```gdscript
class_name ThemeInfo
extends Resource

@export var tileset: StringName
@export var platforms: TilePack
@export var walls: TilePack
@export var background: Array[TileId]
```

`tileset` is a resource path to the built TileSet. `ThemeApplyer` loads it at runtime.

# Source Asset Format

The build pipeline reads `meta.slices` from the theme JSON. It ignores frame data, bounds and colors. Only slice names matter; each slice is expected to have a sibling PNG with exactly the same name.

Example slice names:

```text
background_01
platform_single_01
platform_single_all_01
platform_top_01
walls_full_01
```

## Slice Naming

```text
background_<variant>
platform_<tile_type>_<variant>
walls_<tile_type>_<variant>
```

The variant is the trailing numeric portion of the slice name. The loader extracts it with a regular expression that matches `_<digits>` at the end of the name, before any remaining suffix.

## Tile Types

```text
single
single_all
single_top
single_bottom
single_left
single_right
top
bottom
left
right
full
top_left
top_right
bottom_left
bottom_right
```

## Texture Convention

For a slice named `platform_top_left_01`, the loader expects:

```text
res://assets/sprites/themes/{theme}/platform_top_left_01.png
```

A missing texture is a fatal build issue.

# Build Pipeline

`ThemeBuilder` runs a `BuildStep` pipeline against a `ThemeBuildContext`.

Default order:

```text
ThemeAssetsLoadStep
→ TileSetBuildStep
→ ThemeSaveStep
```

Like the room bake pipeline, it stops before a step when the report has a fatal issue or the step cannot run with errors.

## Context

```gdscript
class_name ThemeBuildContext
extends RefCounted

var theme_name: String
var theme_tile_assets: ThemeTileAssets
var theme_info: ThemeInfo
var tileset: TileSet
var report: ThemeBuildReport
```

The context derives all output paths from `theme_name`:

```text
res://resources/themes/{theme}/{theme}_tile_assets.tres
res://resources/themes/{theme}/{theme}_theme.tres
res://resources/themes/{theme}/{theme}_tileset.tres
```

## Reporting

`ThemeBuildReport` groups `ThemeBuildIssue` objects by issue type. Each issue has a severity: `WARNING`, `ERROR` or `FATAL`.

Issue types:

- `FILE_NOT_FOUND`
- `JSON_PARSE_ERROR`
- `INVALID_JSON_STRUCTURE`
- `INVALID_SLICE_NAME`
- `UNKNOWN`

An unparseable slice name is a warning and the slice is skipped. Missing source files, invalid JSON and texture load failures are fatal.

## 1. ThemeAssetsLoadStep

**ID:** `theme_assets_load`

Reads the theme JSON and builds a `ThemeTileAssets` catalog.

- Parses each slice name into category, tile type and variant.
- Groups variants into `platforms` and `walls`.
- Collects background variant names.
- Emits warnings for slices that cannot be parsed.

## 2. TileSetBuildStep

**ID:** `tileset_build`

Builds a `TileSet` and resolves the asset catalog into `ThemeInfo`.

For every unique asset name:

1. load the matching PNG;
2. create one `TileSetAtlasSource` containing a single tile at `(0, 0)`;
3. register it in the `TileSet`;
4. add a solid collision polygon for platform and wall tiles.

Builds a `TilePack` for platforms and walls, and an `Array[TileId]` for background.

Current implementation details:

- tile size is hardcoded to `32 × 32`;
- each texture becomes its own atlas source;
- collision is a full 32 × 32 box, added only for `platform_*` and `walls_*` tiles;
- background tiles receive no collision.

`WorldSettings.tile_size` is currently also `32`, but the theme build step does not read it.

## 3. ThemeSaveStep

**ID:** `theme_save`

Saves the three built resources:

```text
{theme}_tile_assets.tres
{theme}_theme.tres
{theme}_tileset.tres
```

# Theme Application

`ThemeApplyer.apply(room_node, theme, room_data)` applies a built theme to an existing runtime room.

It expects the runtime room structure produced by `RuntimeRoomBuilder`:

```text
RuntimeRoom (Node2D)
└── Semantic (Node2D)
    └── Tiles (TileMapLayer)
```

If `Semantic/Tiles` or the theme TileSet cannot be found, application fails with an error.

## Application Order

1. assign `theme.tileset` to the `TileMapLayer`;
2. place background cells from `RoomData.background`;
3. place platform cells from `RoomData.platforms`;
4. place wall cells from `RoomData.walls`.

## Tile Selection

Platform and wall selection uses the semantic cell's shape and corner data.

```text
FULL                          → full
SINGLE + corners ALL          → single_all
SINGLE + corners NO           → single
SINGLE + other corner values  → single_<corner>
other shape + corners NO      → <shape>
other shape + other corners   → <corner>
```

Names are lowercased and resolved against the corresponding `TilePack`.

Background selection uses `RoomData.background` cell positions and the theme background array.

## Variant Selection

When a pack field contains multiple variants, the applyer chooses one at random:

```gdscript
randi() % array.size()
```

The current implementation does not use cell position to choose a deterministic variant. Rooms may therefore look different between runs even with the same theme and data.

## Default Theme During Bake

`ApplyDefaultThemeStep` loads:

```text
res://resources/themes/default/default_theme.tres
```

and applies it to the generated runtime room before the room is saved. This makes the baked runtime scene previewable in the editor.

The runtime is free to apply a different theme later; the bake step exists only to produce a themed default artifact.

# Current Scope

Implemented:

- Aseprite JSON slice parsing;
- variant catalogs for background, platforms and walls;
- TileSet generation from per-slice textures;
- solid collision for platform and wall tiles;
- `ThemeInfo` and `TilePack` generation;
- saving built theme resources;
- theme application to `RoomData` cells;
- default theme application during room baking.

Not yet implemented:

- theme selection by biome or progression;
- deterministic variant selection;
- tile size from `WorldSettings`;
- atlas packing multiple tiles into one texture;
- animated tiles;
- decoration, prop or foreground layers;
- theme validation beyond build-time issue reporting;
- runtime theme streaming or hot reload.

---

# Design Rules

- A theme must not change room topology, collision semantics or `RoomData`.
- Theme building and theme application remain separate responsibilities.
- Semantic data describes meaning; themes describe appearance.
- Do not put room topology or gameplay semantics into a theme.
- Do not make baking depend on a specific biome theme.
